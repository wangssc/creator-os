# 账号诊断（R-D01 ~ R-D04）施工规格

> 来源：`docs/01-PRD.md` 第 6.8 节（US-24/25/26）、第 7.8 节（R-D01~R-D04 为 P0，R-D05/R-D06 需平台授权、本期不做）。
> 现状：`static/index.html` 里 `pageDiagnose()` 的界面**已经画好**，但数据来自 `MOCK.diagnose`，`diagRun()` 只是 `setTimeout` 假装跑完，导航还被 `LATER_MODULES` 拦住。本次只做「把假的换成真的」。

## 一、目标（一句话）

用户把账号近期的内容数据贴进来（或传 CSV），系统算出四项指标、画一周走势、给出可执行建议——**每一项都能追到具体某一行数据**。

## 二、**不要做**什么（先看这一段，比做什么更重要）

1. **不接任何平台接口**。R-D05 需要公众号/小红书/抖音授权，本期不做，也不写「即将支持」的假按钮。
2. **不编数据**。某项算不出来（比如用户没填粉丝数），返回 `null` 并在界面显示「—」，**不要填 0、不要填示例值**。
3. **不改 `prompts/` 下的任何文件**。评语 prompt 单独新增一个 `prompts/diagnose.md`。
4. **不动已有路由和已有页面**。`app.py` 只追加，不修改现有函数。
5. **不加新依赖**。CSV 用标准库 `csv`，Excel 不支持（明确拒绝，返回「请另存为 CSV」）。
6. **不改 `MOCK` 对象本身**——`MOCK.diagnose` 保留（演示模式还要用），只是正常路径不再读它。

## 三、数据从哪来（R-D01）

### 3.1 输入格式（固定四列 + 三个可选列）

必填：`标题` `平台` `阅读`
可选：`发布时间` `点赞` `转发` `评论` `粉丝数`

**表头允许同义写法**（用户从各种后台导出来的名字不一样），接受这两组：

| 标准名 | 也接受 |
| --- | --- |
| 标题 | title / 内容 / 作品 |
| 平台 | platform / 渠道 |
| 阅读 | 阅读量 / 播放 / 曝光 / views |
| 发布时间 | 时间 / 发布日期 / date |
| 点赞 | 赞 / likes |
| 转发 | 分享 / 分享数 / shares |
| 评论 | 评论数 / comments |
| 粉丝数 | 粉丝 / fans |

**没有 `标题` 或 `平台` 列 → 直接拒绝**，返回 `{"ok":false,"error":"缺少必需列：标题","detail":"读到的表头是：..."}`。

### 3.2 两种入口（都是主路径，R-D01 明确要求）

- **粘贴**：前端一个 textarea，用户从 Excel 直接 Ctrl+V（Tab 分隔）
- **上传**：`<input type=file accept=".csv">`，UTF-8 与 GBK 都要能读（Excel 导出中文 CSV 默认是 GBK）

### 3.3 落库

新建一张表 `diagnose_runs`：

```sql
CREATE TABLE IF NOT EXISTS diagnose_runs (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  ts          TEXT NOT NULL,          -- 'YYYY-MM-DD HH:MM:SS'
  platform    TEXT NOT NULL,          -- 选中的平台；'全部' 表示跨平台
  row_count   INTEGER NOT NULL,
  score       INTEGER,                -- 0-100，数据不足时 NULL
  payload     TEXT NOT NULL,          -- 完整结果 JSON（metrics/bars/suggestions）
  note        TEXT                    -- LLM 评语；没 key 时 NULL
);
```

建表用 `db.py` 现有的迁移写法（照着 `point_records` 那张表抄）。

## 四、四项指标怎么算（R-D02 + R-D03）

**所有计算只看用户导入的那批数据，不跟任何外部基准比。**「同类账号均值」这类说法一律不许出现在输出里——我们不知道别人的数据。

### 4.1 互动率

`rate = (点赞 + 转发 + 评论) / 阅读`，阅读为 0 或缺失时该行**不计入**（不是记 0）。

**口径必须复用 `app.py` 现有的 `calc_rate()`**，不许重写一份——README 第 64 行专门强调过「不允许在别处再实现一遍，否则前后端口径分叉」。

### 4.2 四项指标（对应界面四个 KPI 卡）

| 界面 label | 怎么算 | pct（进度条） |
| --- | --- | --- |
| 内容质量 | 四项子分加权，见 4.3 | 分值本身（0–100） |
| 粉丝增长 | 若数据里有 `粉丝数`：末值/首值 − 1；否则 **null** | 有值按 `min(100, 增长% × 10)`，null 时 0 |
| 互动率 | 全部有效行的加权平均（总互动 / 总阅读），单位 % | `min(100, 互动率% × 20)` |
| 更新频率 | 有效行数 ÷ 覆盖周数（不足一周按一周算） | `min(100, 篇/周 × 15)` |

`value` 是**字符串**（界面直接显示），保留一位小数：如 `"1.8"`。`unit` 固定 `"分"` / `"%"` / `"%"`
`"篇/周"`。

### 4.3 内容质量的四项子分（纯规则，不调模型）

每项 0–100，最后 `质量 = round(选题力×0.3 + 标题力×0.3 + 信息密度×0.25 + 稳定性×0.15)`。

**选题力**（看标题里有没有「具体的谁」和「具体的事」）：
- 标题含数字 → +25
- 标题含疑问词（为什么/怎么/如何/吗/呢/哪/谁）→ +20
- 标题含具体人群词（我/你/普通人/学生/宝妈/程序员/上班族/退休/50岁…）→ +25
- 标题长度 8–28 字 → +20，<8 或 >40 → +0，其余 +10
- 标题含抽象大词（格局/认知/思维/底层逻辑/干货/必看）→ −15（这类词人人可用，等于没信息）
- 封顶 0–100

**标题力**：
- 最高分与最低分的阅读差距 / 最高分（离散度）→ 这是「标题能不能决定结果」的直接证据，映射 0–100
- 样本 <3 条时这一项返回 null，质量分改按其余三项重新归一

**信息密度**（用户导入的数据里没有正文，只能用代理指标）：
- 阅读中位数 ÷ 阅读均值。中位数远低于均值 = 少数爆款撑起来的，说明大部分内容偏弱 → 比值越低分越低
- 具体：`ratio = median/mean`，`分 = round(min(100, ratio × 100))`

**稳定性**：
- 阅读的标准差 ÷ 均值（变异系数 CV），CV 越小越稳
- `分 = round(max(0, 100 − CV × 100))`

### 4.4 一周走势（`bars`，7 根柱子）

按 `发布时间` 的**星期几**聚合，取该星期几所有行的**阅读中位数**（不用均值，避免一条爆款把整根柱子拉爆）。

- 没有 `发布时间` 列 → `bars` 返回 `[]`，界面把这块面板换成一句「这次导入没带发布时间，看不出周内分布」
- 某天没数据 → 该根柱子 `v: 0`，并在该柱子上标 `empty: true`（界面用灰色）
- `v` 是像素高度 0–96，按当天值 ÷ 最大值 × 96
- 最高的那天标 `hot: true`

### 4.5 异常点（R-D03 的「异常点标记」）

对每一行算 `rate`，再算全体 `rate` 的中位数与 MAD（绝对中位差）。
`|rate − 中位数| > 3 × 1.4826 × MAD` 的行标为异常，在 UI 的建议区单列一条：
「《标题》的互动率 6.9%，是你这批数据里明显偏离的一条（中位数 2.1%）」

MAD 为 0（大多数行完全一样）时不标异常。

## 五、建议怎么生成（R-D04）

**先走规则，规则出不了再让模型说一句。** 顺序不能反。

规则建议器（纯 Python，必定有输出）：

| 触发条件 | 建议文案模板 |
| --- | --- |
| 互动率 < 1% | 「互动率 {x}%，低于 1%。检查结尾有没有具体提问——不是『你怎么看』，而是『你上次遇到这种情况是怎么处理的』。」 |
| 互动率 ≥ 5% | 「互动率 {x}%，这个数字说明你的读者愿意动手。把这批里互动率最高的那篇的结尾句式抠出来，当成模板固定。」 |
| 更新频率 < 2 篇/周 | 「近 {n} 周只发了 {m} 篇，平均 {x} 篇/周。平台对更新频率的权重通常高于单篇质量，先做到每周 2 篇再谈优化。」 |
| 更新频率 > 7 篇/周 | 「{x} 篇/周属于高频。这个节奏下质量通常会被稀释——把这批里互动率最低的三篇找出来，看它们是不是赶工出来的。」 |
| 阅读 CV > 1.5 | 「阅读量忽高忽低（变异系数 {x}）。这说明你的选题还没形成可复用的模式，靠碰运气。先把跑赢的三篇放在一起找共同点。」 |
| 有异常点 | 「《{标题}》是这批里唯一明显偏离的（{rate}%，中位数 {median}%）。单独分析它，别混在平均里。」 |
| 质量分 < 60 | 「内容质量 {x} 分，主要失分在{最低的那一项}。这一项是可以靠模板化的方式改的，优先动它。」 |
| 质量分 ≥ 85 | 「内容质量 {x} 分。这个水平下继续优化文字的收益已经很小，把精力挪到分发——同样的内容换一个平台、换一个标题重发一次。」 |
| 以上都不触发 | 「这批 {n} 条数据没有明显异常。想看出问题，需要至少 10 条或跨两周的数据。」 |

**最多输出 3 条**，按「影响面 × 可执行性」排序：异常点 > 互动率 > 更新频率 > 质量分 > 稳定性。

LLM 评语（可选增强，`prompts/diagnose.md`）：
- 只在 `ZHIPU_API_KEY` 配了的时候调
- 输入是**算好的指标 + 规则建议**，让模型做「一句话总评 + 指出规则没覆盖到的东西」
- 模型失败 → 整条链路仍然成功，`note` 返回 null，界面不显示这一段
- **prompt 里必须写死**：只能引用输入里的数字，不许编造用户没提供的信息

## 六、接口（四个）

统一用现有的 `ok()` / `fail()` 包装（`app.py:29/34`）。

### `POST /api/diagnose/import`
```json
// 请求
{"platform": "小红书", "csv": "标题,平台,阅读\n...", "filename": "导出.csv"}
// 或 multipart：file=@x.csv&platform=小红书
// 响应
{"ok": true, "run_id": 12, "row_count": 20, "skipped": 2,
 "columns": {"标题": true, "平台": true, "阅读": true, "发布时间": false, ...}}
```
`skipped` 是被丢弃的行数（缺标题或缺阅读），界面要显示「已读 20 行，跳过 2 行（缺标题）」。

### `POST /api/diagnose/run`
```json
// 请求：{"run_id": 12}
// 响应（形状必须与 MOCK.diagnose 完全一致，前端直接替换不用改渲染）
{"ok": true,
 "metrics": [{"label":"内容质量","value":"72","unit":"分","pct":72}, ...],
 "bars":    [{"l":"周一","v":42}, {"l":"周五","v":96,"hot":true}, ...],
 "suggestions": ["...", "...", "..."],
 "note": "一句话总评" | null,
 "anomalies": [{"title":"...","rate":0.069,"median":0.021}],
 "score": 72}
```

### `GET /api/diagnose/runs?limit=10`
历史记录列表（`id / ts / platform / row_count / score`）。

### `GET /api/diagnose/runs/{id}`
回看某次的完整结果（直接返回落库的 payload）。
